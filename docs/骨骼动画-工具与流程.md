## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 1. 工具是什么 | **Esoteric Software 的 Spine 编辑器**。本工程骨骼版本串 `4.2.43` ⇒ 需要 **Spine 4.2.x** 编辑器 |
| 2 ★ 没有 `.spine` 能否导回编辑器改 | **能。官方明确支持**：`Import Data` 可导入 Spine 自己导出的 **JSON 或 binary**，用途之一就是官方博客标题所说的「**你手里没有 Spine 工程文件，只有导出文件**」的场景 |
| 3. 版本锁定 | **是，锁定在 major.minor**。运行时用 `startsWith` 比对版本串：`4.2.x` 的数据只能被 `4.2` 运行时读；4.1/4.0/4.3 都不行。`4.2.43` 数据 + `4.2` 运行时 **可读** |
| 4. 免费/替代路径 | **没有可用的免费导出路径**。Spine 试用版**不能保存工程、不能导出**（官方页面明确列出）；DragonBones 官方 README 未声明支持 Spine 格式 |
| 5. 端到端流程 | Spine 4.2 重开工程 → 加动画 → 二进制导出 → 覆盖仓库 `.skel` → Godot 重导入 → 打包 `.pck`（本地工具链已成熟） |
| 6. 命名与触发 | **`low_health_loop` 是游戏 C# 层硬编码的动画状态名**，已在本机实测到精确日志。骨架里存在的名字是 `idle_loop / attack / cast / die / hurt / relaxed_loop` |

### 推荐路径（按可行性排序）

**A. 正解（要能改骨骼本体）**：找一个 **Spine 4.2.x** + **Professional** 许可的人（或自购），按下面第 6 节流程
「解图集 → Import Data 重建工程 → 加 `low_health_loop` → 二进制导出」。这是唯一能真正新增动画的路径。

**B. 零美术绕行（不需要任何 Spine 编辑器）**：游戏是**按名字**在骨架里找动画的
（`SkeletonData::findAnimation` 就是精确名字查找，无别名机制 —— 见 §5 证据）。
所以在**不改 `.skel`** 的前提下，唯一能让 `low_health_loop` 出现的办法是让引擎去找一个**已存在的**动画名，
即用 BaseLib 的 `SetupCustomAnimationStates` / `SetupAnimationState` 把残血状态**映射到已有动画**
（例如 `relaxed_loop` 或 `idle_loop`）。这条路**不动骨架、不改 `.skel`**，
但要改 C# 代码（本仓库的皮肤管理器已在链路里，见 §7 附注）。
另外本机已装有一个同作者写的先例 mod `CharacterSkinAnimFix`，其做法就是「探测骨架里有哪些动画，再做别名」——
可作为实现参考（见 §7）。

> ⚠️ 注意：**Spine 试用版救不了你** —— 它连导出都不允许，而我们需要产出一个新的 `.skel`。

## 1. 工具是什么

**结论：Esoteric Software 的 Spine 编辑器。** 不是 DragonBones、不是 Godot 原生骨骼。

证据链：

- 骨骼文件是 Spine 自有二进制格式。本仓库 8 个 `.skel` **全部**解析出同一个版本串：
  ```
  @0  byte  len = 0x07        # 版本串长度 = 7
  @1  ascii "4.2.43"          # 版本串
  @8  ...                     # 骨架数据
  ```
  实测（`tools/restore-sources.py` 同款判据）：
  | 文件 | 版本 |
  |---|---|
  | `animations/orca_plate/characters/ironclad/ironclad.skel` | `4.2.43` |
  | `animations/Orcaweddingdress/characters/ironclad/ironclad.skel` | `4.2.43` |
  | `orca_plate/character_select/.../characterselect_ironclad.skel` | `4.2.43` |
  | `orca_plate/merchant/.../ironclad.skel` | `4.2.43` |
  | `orca_plate/rest_site/.../restsite_ironclad.skel` | `4.2.43` |
  | （婚纱侧四个同理） | `4.2.43` |
  → 本地实测；同款判据亦见 `docs/踩坑指南.md:434`（`.spskel` = 8 B 头 + Spine 数据，偏移 9 起是版本号如 `4.2.43`）

- 游戏侧运行时是 **spine-godot**，来自官方 spine-runtimes 仓库：
  游戏根目录 `libspine_godot.windows.template_release.x86_64.dll` 内含源码路径字符串
  `spine_godot\spine-cpp\src\spine\SkeletonBinary.cpp`、`spine_godot\SpineAnimationState.cpp`、
  以及编译路径 `D:\a\spine-runtimes\spine-runtimes\spine-godot\spine_godot\SpineCommon.h`
  → 本地实测（该 dll 的 ASCII 字符串表）
- 官方文档把 spine-godot 定位为「加载、播放和操作**由 Spine 创建**的动画」的运行时
  → <https://esotericsoftware.com/spine-godot>（中文页 <https://zh.esotericsoftware.com/spine-godot/markdown>，
  原文：「spine-godot运行时支持加载、播放和操作由Spine创建的动画」）

**版本要求：Spine 4.2.x。** 依据是 §3 的版本锁定规则（major.minor 必须与运行时一致）。
本机游戏 `release_info.json` 为 `version: v0.111.0, branch: v0.111.0`（本地实测）。

## 2 ★ 最关键：没有 `.spine` 源工程，能不能把 `.skel` 导回 Spine 编辑器改？

### 结论：**能。官方明确支持，且官方专门为此写了一篇博客教程。**

但有一个**必须先检查**的开关 —— `Nonessential data`（非必要数据）：

- 若当初导出时**勾了** `Nonessential data`，导回来几乎无损；
- 若**没勾**（运行时导出的默认做法），**导入会成功，但会丢信息**。

### 一手证据

**(a) 官方 `Import` 文档 —— 明确写着可以导入自己导出的 JSON / binary：**

> Spine can import data in the [JSON] or [binary] formats that it [exports]. This provides a path to bring data from other programs into Spine, such as from image editor scripts.
>
> It can be useful to **recreate a Spine project from JSON or binary data and a texture atlas**. To do that, see the [Importing skeleton data] blog post.

→ <https://esotericsoftware.com/spine-import#Data>（原文照录）

同页 `Nonessential data` 节：

> When JSON or binary data is exported and the `Nonessential data` setting is checked, extra information is exported which is not normally used at runtime. **If the data is later imported back into the Spine editor, that extra information is used to configure the imported skeleton.**
>
> If JSON or binary data is exported **without** `Nonessential data` being checked and is later imported back into the Spine editor, then **the import will succeed but some information may be lost.**
>
> For example, the color of a bounding box is not normally needed at runtime... If that exported data is imported back into the Spine editor, the bounding box will have a default color.
>
> For mesh attachments, the manual (orange) edges inside the mesh hull are nonessential data. If `Nonessential data` is not checked... the mesh will not have any manual edges. The triangulation of the mesh from when it had manual edges is preserved.

→ 同上 URL

**(b) 官方博客《Importing skeleton data》—— 开篇第一句就是我们这个场景：**

> There are cases where **you have no Spine project but want to import a skeleton into Spine using exported files.** This tutorial will guide you through the process.

→ <https://esotericsoftware.com/blog/Importing-skeleton-data>（2023-04-18）

**(c) 官方 `Versioning` 文档 —— 把「导出文件当长期存储」的坑和正确姿势都写明了：**

> **Exported JSON or binary files are not a good choice for storage.** They can be imported back into the Spine editor, but **only into the same version that exported the data**. If nonessential data was not exported, importing the data back into Spine will lose some information. **Once imported, a Spine project file can be saved and that can be opened in a new version of the Spine editor.**

并且给了 **CLI 批量做法**（原文示例）：

```
Spine -u 3.6.51 -i input.json -o project.spine --import
Spine -u 4.0.10  -i project.spine -o path/to/exports --export json
```

→ <https://esotericsoftware.com/spine-versioning#File-storage>

**(d) 运行时源码证据：`Nonessential` 标志确实写在文件里**（所以「勾没勾」是可查的）：

```cpp
nonessential = readBoolean(input);
if (nonessential) {
    skeletonData->_fps = readFloat(input);
    skeletonData->_imagesPath.own(readString(input));
    skeletonData->_audioPath.own(readString(input));
}
```

→ <https://github.com/EsotericSoftware/spine-runtimes/blob/4.2/spine-cpp/spine-cpp/src/spine/SkeletonBinary.cpp>（`SkeletonBinary::readSkeletonData`）

### 所以「业界通行做法」是什么？

**没有「反编译 `.skel` 回 `.spine`」这回事** —— 但**根本不需要反编译**。
通行做法就是官方博客那一条：**把 `.skel` 当数据源，用同版本 Spine 的 `Import Data` 重建一个 `.spine` 工程，然后正常编辑。**
`.skel` / `.json` 在这里的角色是**可回灌的数据源**，不是只读的编译产物。

> 对本仓库的直接含义：`docs/踩坑指南.md:423` 那条「导入产物就是源文件本身」的结论，
> 在 Spine 这一格上得到了官方文档的确认 —— `.skel` **足以重建工程**。

### ★ 本工程具体的两个前提（已实测，直接决定导入参数）

两条目标骨骼的 atlas 头都是 **预乘 alpha + 非 1 倍打包比例** —— 这两个值必须原样喂给导入流程，否则尺寸/边缘会错：

| 目标 | atlas 首行 | `pma` | `scale` | 区域数 |
|---|---|---|---|---|
| 板甲 `orca_plate` | `ironclad.png` / `size:3091,3091` / `filter:Linear,Linear` | `true` | **0.8** | 164 |
| 婚纱 `Orcaweddingdress` | `ironclad.png` / `size:3900,3900` / `filter:Linear,Linear` | `true` | **0.9** | 179 |

（本地实测，读 `animations/*/characters/ironclad/ironclad.atlas` 头 5 行）

官方博客对这两个值的要求（原文）：

> Check to see if the atlas file has a line specifying the atlas' scale. This information will be needed when importing.
>
> If the atlas was packed with **premultiplied alpha**, Spine needs to **unpremultiply the alpha when unpacking**. For an atlas packed with newer versions of Spine, the atlas file knows that the atlas images have premultiplied alpha. The unpacker will use this information from the atlas file, if it exists.
>
> Your atlas was packed with a scale greater or less than 1. Import the skeleton again and **specify the same scale value that was used to pack the atlas**.

→ <https://esotericsoftware.com/blog/Importing-skeleton-data>

## 3. 版本兼容：`.skel` 是否版本锁定？

### 结论：**锁定在 `major.minor`。**

- **`4.2.43` 的导出 → 能被 `4.2` 系运行时读** ✅（因为比对用的是 `startsWith`）
- `4.2.43` 的导出 → `4.1` / `4.0` / `4.3` 运行时 **都不能读** ❌
- **反向**（4.1/4.0 的数据给 4.2 运行时，或 4.3 的数据给 4.2 运行时）同样 **不行** ❌

### 一手证据

**(a) 运行时源码 —— 锁的是「前缀」，不是完整版本号：**

```cpp
char *skeletonDataVersion = readString(input);
skeletonData->_version.own(skeletonDataVersion);

if (!skeletonData->_version.startsWith(SPINE_VERSION_STRING)) {
    char errorMsg[255];
    snprintf(errorMsg, 255, "Skeleton version %s does not match runtime version %s",
             skeletonData->_version.buffer(), SPINE_VERSION_STRING);
    setError(errorMsg, "");
    ...
    return NULL;
}
```

→ <https://github.com/EsotericSoftware/spine-runtimes/blob/4.2/spine-cpp/spine-cpp/src/spine/SkeletonBinary.cpp>
（`SkeletonData *SkeletonBinary::readSkeletonData`）

**这条同时解释了两件事**：
1. 为什么 `4.2.43` 数据配 `4.2` 运行时**能**跑（`"4.2.43".startsWith("4.2")` 为真）；
2. 为什么必须拿到 **4.2 而不是 4.3** 的编辑器 —— 4.3 编辑器导出的是 `4.3.xx`，前缀对不上。

**(b) 本机游戏运行时的同一条错误串（本地实测，二进制级证据）：**

`libspine_godot.windows.template_release.x86_64.dll` 内含：
```
Skeleton version %s does not match runtime version %s
```
→ 说明游戏用的这个 spine-cpp 副本**带着同一个版本门禁**。

> 附注：本机两个目标骨骼是 `4.2.43`，只要运行时分支是 `4.2` 就能读；这解释了为什么现在游戏能正常显示这两套皮肤。

**(c) 官方 `Versioning` 文档 —— 权威表述：**

> **The major and minor version for the Spine editor used to export JSON or binary data must always match the Spine Runtimes version. If not, the Spine Runtimes will not be able to read the data. This dependency is very important.**
>
> After updating the Spine Runtimes to the branch for the new version, the Spine Runtimes will no longer be able to read any of the exports from the older Spine editor version. All of the Spine projects need to be exported again using the newer Spine editor version.

以及补丁版安全性：

> It is **always safe** to update your Spine editor to a newer **patch** version... For example, if you are using `3.6.44`, you can update to the newer `3.6.53` without worrying that something breaks or that your exports will no longer work with the `3.6` Spine Runtimes.

→ <https://esotericsoftware.com/spine-versioning#Synchronizing-versions>

**(d) 工程文件（`.spine`）的方向性 —— 与本任务的「重建」路线直接相关：**

> Spine project files are **backward compatible, but not forward compatible**. A newer Spine editor version can always open Spine project files saved from any older version. However, once a project is saved, it can no longer be opened by older Spine editor versions.

并且给了「回退」的官方手法，正是 `Import Data`：

> To attempt to recover the work, you can use **JSON export** and set the `Version` to the older Spine editor version... Next, run the older Spine editor version and use **data import** to bring the JSON data into Spine.

→ <https://esotericsoftware.com/spine-versioning#Project-files>

**⇒ 实操结论：在 Spine 4.2 里 `Import Data` 重建工程后，务必「另存为 `.spine`」并把这个工程文件纳入版本管理。**
之后就能用更新的 Spine 打开它（向后兼容），彻底摆脱「只有 `.skel`」的困境。

### 运行时（MegaDot / spine-godot）支持哪个 Spine 版本，从哪确认？

- **官方确定版本的方式**：`spine-runtimes` 用 **Git 分支**对应版本，每个运行时的 `README.md` 写明它对应的确切版本
  > The [default branch] works with the latest non-beta version of Spine. **Each runtime's README.md file lists the exact version it works with.**
  > Git branches are used for each version of the Spine Runtimes. Git commits to a branch are used instead of patch version numbers.
  → <https://esotericsoftware.com/spine-runtime-architecture#Versioning>、<https://esotericsoftware.com/spine-versioning#Spine-Runtimes-version-numbers>
- **本项目的最强证据是「文件本身 + 运行时门禁」**：骨骼版本串 `4.2.43`（实测）+ 运行时 `startsWith` 门禁（源码）⇒ **游戏用的必须是 `4.2` 分支**。
- ⚠️ 无法从 `libspine_godot...dll` 的 PE 版本资源读出运行时版本（`FileVersion` / `ProductVersion` 均为空，本地实测），
  且 `.pck` 头部 64 MiB 扫描未命中明文 `4.2.43`（pck 为压缩存储，本地实测）。
  **⇒ 「游戏内置 spine-godot 的确切提交号」属于未确认项**（见 §8）。

## 4. 免费 / 替代路径

### 4.1 Spine 试用版 —— 对本任务**无用**

官方试用页原文（限制条款）：

> Explore Spine firsthand by downloading the Spine trial, free for Windows, Mac and Linux.
> **All Spine Professional features are available in the trial except saving projects, texture packing, and exporting animation data, images and video.**

→ <https://esotericsoftware.com/spine-download>

**逐条对照本任务**：

| 该动作 | 试用版 | 对本任务的影响 |
|---|---|---|
| 导入 `.skel` 重建工程 | ✅ 可以（属于 Professional 功能，试用开放） | 能**看**、能**改** |
| **保存 `.spine` 工程** | ❌ **禁止** | 干完活存不下来 |
| **导出动画数据（`.skel`/`.json`）** | ❌ **禁止** | **产不出要替换的文件 ⇒ 试用版直接出局** |
| 打包 texture atlas | ❌ 禁止 | 不影响（我们复用现有图集） |

> **所以试用版只能用来「评估」和「确认能不能导入」，不能用来交付。**

### 4.2 DragonBones

- 官方 README **没有**声明支持 Spine 格式，其支持面是自家格式 + 自家引擎/`LoongBones` 工具：
  > ## Highly suggest use [LoongBones](http://www.loongbones.app/) to create animation.
  > ## Supported engines
  > Egret / PixiJS / Phaser / Hilo / Cocos creator
  → <https://github.com/DragonBones/DragonBonesJS>（README）
- 且它是**另一套骨骼格式**，即使能导出，产物也不是 spine-godot 能读的 `.skel`/`.atlas`。
- **⇒ 「DragonBones 替代 Spine 改 StS2 骨骼」不成立。** 官方 README 未提及 Spine 格式支持（未确认清单里也记一笔：官方未对此做**否定性**声明，属「未声明」而非「明确不支持」）。

### 4.3 开源库能读写 Spine 4.2 数据吗？

- **能读**：官方 `spine-runtimes` 全量开源，含各语言运行时（`spine-cpp`、`spine-c`、`spine-ts`、`spine-godot` 等）
  > The source code for the Spine Runtimes is available in its entirety on [GitHub].
  → <https://esotericsoftware.com/spine-runtime-architecture#Source-code>
- **但「读」≠「能产出编辑器可编辑的工程」**：运行时的 `SkeletonBinary` 是**只读解析器**，
  它把数据读成运行时对象（`SkeletonData`/`Animation`/`Timeline`），**没有任何写回 `.skel` 或写成 `.spine` 的能力**。
  > Run 时 API 说明：「无法直接创建、添加或删除骨骼、槽位和其他Spine对象」（spine-godot 的 GDScript 暴露限制）
  → <https://zh.esotericsoftware.com/spine-godot/markdown>（「访问Spine运行时API」节）
- **⇒ 结论：不存在「用免费/开源库生成新动画再写回 `.skel`」的现成可行路径。**
  唯一能产出可编辑工程或新 `.skel` 的官方途径是 **Spine 编辑器本体（含 `Import Data` 与 CLI `--import`/`--export`）**。
- 官方 CLI 是**编辑器自带的**，不是独立免费工具：
  > Spine project files and JSON or binary data can also be imported using the [command line interface].
  → <https://esotericsoftware.com/spine-import#Import>

## 5. 动画命名与触发：`low_health_loop` 从哪来？

### 5.1 它是**游戏 C# 层硬编码的状态名**（本地实测，最硬的证据）

本机 `sts2.dll` 的用户字符串堆里**直接存在** `low_health_loop` 字面量，
且与其它动画状态名挤在同一段（同一批常量）：

```
... event:/sfx/characters/ . _select . _attack . _cast . _die
    event:/sfx/ui/wipe . Cast . Attack . Hit . PowerUp
    idle_loop . low_health_loop . relaxed_loop . Idle . Relaxed . Dead ...
```
→ 本地实测：`D:\Steam\steamapps\common\Slay the Spire 2\data_sts2_windows_x86_64\sts2.dll`
  （UTF-16 字符串，偏移 ≈ 4 219 328）

同文件另一处还带着**报错模板本身**（连同占位符顺序）：

```
... anyState . could not find '.' animation on '.' animation (queued) on '.
    ActNumber . ActName . %Banner ...
```
→ 本地实测，偏移 ≈ 4 310 539

**这两条串拼起来，与实测日志逐字吻合** ⇒ 该报错**不是 spine-godot 打的，是游戏 C# 层打的**：

```
[WARN] could not find 'low_health_loop' animation (queued) on 'Visuals'
```
→ 本地实测：`C:\Users\34294\AppData\Roaming\SlayTheSpire2\logs\godot2026-10-06T15.40.57.log:6300`（另有 6321/6500/6528/6536/6545/6585/6592/6608 等 10+ 处）

> **反证（很重要，别被误导）**：spine-godot 自己的报错文案是

### 5.5 顺带查到：游戏动画状态的命名族（`sts2.dll` 字符串实测）

→ 本地实测，`sts2.dll` UTF-16 字符串表（`^[A-Za-z][A-Za-z0-9_]*$` 过滤后人工归类）。

## 6. 端到端流程（细到「下一步点哪里」）

### 阶段 0：准备（一次性）

- [ ] **拿到 Spine 4.2.x + Professional 许可**（试用版不行，见 §4.1）。
      启动器里选 **`Specific version` → `Other...` → 填 `4.2.43`**（或 4.2 系任一版本；补丁号升级是安全的）。
      > 版本选择入口：<https://esotericsoftware.com/spine-versioning#Choosing-a-Spine-editor-version>
      > 「When Spine starts, the launcher window allows choosing which version of the Spine editor to use.」
- [ ] **先验证 Nonessential 标志**（决定后面有没有损失）：
      `.skel` 里 `nonessential` 是紧随 `referenceScale` 之后的一个 bool。
      更省事的办法：直接导入后肉眼比对「骨骼图标是否全变默认、骨骼颜色是否复位、mesh 手动边是否消失」——
      官方博客列的正是这三个症状（<https://esotericsoftware.com/blog/Importing-skeleton-data> 的 Troubleshooting）。
- [ ] 复制一份目标骨骼到工作目录（**别在原仓库上直接操作**）：
      `animations/orca_plate/characters/ironclad/{ironclad.skel, ironclad.atlas, ironclad.png}`

### 阶段 1：解包 texture atlas（把整图还原成单张切图）

- [ ] Spine 主菜单 → **`Texture Unpacker`**
- [ ] `Atlas` = 上面的 `.atlas` 路径
- [ ] `Output folder` = 单图输出目录
- [ ] `Unpremultiply alpha` —— **必须勾上**（两个 atlas 都是 `pma:true`；
      新版 Spine 会读 atlas 里的 `pma:true` 自动生效，但显式勾上更稳）
      > 「Check `Unpremultiply alpha` if the atlas was packed with premultiplied alpha. If the atlas file has "pma:true", that will be used instead of this checkbox.」
- [ ] 点 **`Unpack`**
- 命令行等价写法：
      ```
      Spine --input <atlas图所在目录> --output <单图输出目录> --unpack <atlas文件>
      ```
      可加 `-u 4.2.43` 指定版本，或 `-u latest`（**解包**用最新版更好）。
- ⚠️ **不要漏 `scale`**：板甲是 `0.8`、婚纱是 `0.9`。这一步产出的单图是**已经缩放过的**尺寸，
      下一步的 `Scale` 输入框要与之对齐。

### 阶段 2：`Import Data` 重建 `.spine` 工程

- [ ] 主菜单 → **`Import Data`**
- [ ] `File` = `.skel` 路径
- [ ] **`Scale` = 上表的 atlas scale**（板甲 `0.8` / 婚纱 `0.9`）
      > 「If the texture atlas was scaled, set the `Scale` value so the size of the skeleton will match the unpacked atlas images.」
      > ⚠️ 官方同页也警告：`Scale` 会**等比改变骨骼的尺寸但不改骨骼 scale**，全量数据（骨骼位置/长度、附件偏移、包围盒、mesh、动画）都会被缩放。
- [ ] `Name` = 骨架名（如 `ironclad`）
- [ ] 勾 **`New project`**（导入成新工程）→ 点 **`Import`**
- [ ] **此时会看到 `MISSING` 占位图** —— 这是**预期行为**，因为 image path 还没设。**先 `Save` 工程**（存成 `.spine`）。
      > 「Press `Import` and you will see your skeleton, but with `MISSING` images instead of the correct images. This happens because the image path has not been set... First, save the Spine project.」
- [ ] 左侧 `Tree` 里选中 **`Images`** 节点 → 在 `Path` 里填阶段 1 的单图目录
- [ ] 现在图像应该正确显示了。

**疑难对照**（官方博客 Troubleshooting 直接抄）：
| 症状 | 原因 |
|---|---|
| 图像不显示（即使 path 对） | 骨架用了 Professional 特性，而你用 Essential 导入 ⇒ **必须用 Professional** |
| 透明区有**暗**边 | 解包时漏勾 `Unpremultiply alpha` |
| 透明区有**白**边 | 解包时**多勾**了 `Unpremultiply alpha` |
| 部件尺寸偏大/偏小 | `Scale` 没填对（板甲 0.8 / 婚纱 0.9） |
| **动画不正确** | **必须用与导出时相同的 Spine 版本**（→ 这就是 4.2） |
| 骨骼图标全变默认图标 | 骨骼图标信息不在导出数据里，导入必然如此（**无损**） |
| 骨骼颜色复位 / mesh 手动边消失 | **导出时没勾 `Nonessential data`** |

### 阶段 3：新增 `low_health_loop` 动画

- [ ] 切到 **`Animate`** 模式
- [ ] `Animations` 面板 → **`New Animation`** → 名字**精确**输入 **`low_health_loop`**
      （大小写敏感、无空格、无自动别名 —— 见 §5.2 的 `findAnimation`）
- [ ] 做**循环**动画：首尾帧姿态要一致（游戏侧对残血态是按 loop 播的）
- [ ] 建议时长与现有 `idle_loop` 对齐（避免切态跳变）；可在 `SpineSkeletonDataResource` 的
      `animation_mixes` 里配过渡时间（见阶段 5）
- [ ] 如果之后还想用官方 CLI 批处理：`Spine -u 4.2.43 -i project.spine -o <导出目录> --export json`

### 阶段 4：导出

- [ ] 主菜单 → **`Export`**
- [ ] **格式选 `Binary`**（不是 JSON）——
      > 「建议选择二进制格式导出而非JSON导出，因为二进制格式文件尺寸更小，加载更快。如果你必须使用JSON，请确保文件扩展名为 `.spine-json` 而非 `.json`。」
      → <https://zh.esotericsoftware.com/spine-godot/markdown>（「为Godot导出资产」节）
- [ ] **勾上 `Nonessential data`**（本次用不到也必须勾 —— 这是给自己下次留后路）
      > 「If you plan to import data in the future, be sure to check `Nonessential data` when exporting.」
- [ ] ⚠️ **不要重新打包 atlas**（保持原 `.atlas` + 原 `.png` 不动）：
      重新打包会改变 `size`/`scale`/区域顺序，而 `.tres` 与 `pma` 设置是围绕现有图集调的。
      若确实要重打，注意官方警告：**spine-godot 不支持预乘 alpha 导出的 atlas**。
      > 「由于Godot的技术限制，spine-godot运行时目前不支持使用预乘alpha导出的atlas。」
      > —— 现有图集是 `pma:true`，**这是 Godot 侧的既有限制，不要在这里动它**。
- [ ] 导出产物应仍是 `ironclad.skel`（+ 保持原 `.atlas`/`.png`）

### 阶段 5：进 Godot（仓库内）

- [ ] 用新的 `.skel` **覆盖** `animations/orca_plate/characters/ironclad/ironclad.skel`（以及婚纱那条）
- [ ] 确认头部仍是 `07 "4.2.43"`（**别导成 4.3**）：
      ```powershell
      $b=[IO.File]::ReadAllBytes('<path>\ironclad.skel')
      [Text.Encoding]::ASCII.GetString($b,1,$b[0])   # 期望 4.2.43
      ```
- [ ] Godot 会自动检测源文件变化并重导入：
      > 「你只要简单地覆盖这些源文件（`.spine-json`, `.skel`, `.atlas`, `.png`）... Godot编辑器将检测到这些源文件的更改，并自动重导入对应资产」
      > → <https://zh.esotericsoftware.com/spine-godot/markdown>（「更新Spine资产」节）
      若没触发，就在文件的「导入设置面板」里手动强制重导入。
- [ ] 不用手改 `.import`：它由导入器生成，`importer="spine.skel"` / `type="SpineSkeletonFileResource"`，
      并给出 `.godot/imported/<name>-<hash>.spskel` 产物路径
      （本地实测：`animations/orca_plate/characters/ironclad/ironclad.skel.import`）
- [ ] 不用新建 `.tres`（沿用现有），但**建议**在 `SpineSkeletonDataResource` 里给它配过渡时间：
      ```
      [gd_resource type="SpineSkeletonDataResource" load_steps=3 format=3]
      [ext_resource type="SpineAtlasResource" path=".../ironclad.atlas" id="1"]
      [ext_resource type="SpineSkeletonFileResource" path=".../ironclad.skel" id="2"]
      [resource]
      atlas_res = ExtResource("1")
      skeleton_file_res = ExtResource("2")
      default_mix = 0.2
      animation_mixes = {}
      ```
      （本地实测：`animations/orca_plate/characters/ironclad/ironclad_skel_data.tres`）
      `animation_mixes` 就是「动画 mix 时间」的可改入口
      > 「skeleton数据资源也存储了可在检查器中修改的动画mix时间」
      > → <https://zh.esotericsoftware.com/spine-godot/markdown>（「导入至Godot」节）

**`.import` / `.tres` / `.remap` 三者角色（本地实测 + 官方文档）：**

| 文件 | 角色 | 由谁生成 | 要不要手改 |
|---|---|---|---|
| `*.skel.import` | Godot **导入器说明**：`importer="spine.skel"`、`type="SpineSkeletonFileResource"`、`uid`、产物 `path="res://.godot/imported/....spskel"` | Godot 导入器 | ❌ 不用 |
| `*_skel_data.tres` | **把 atlas + skel 组合成一个 `SpineSkeletonDataResource`**，供 `SpineSprite` 使用；含 `default_mix` / `animation_mixes` | 手动 `New Resource...` | ⚠️ **可改**（配 mix） |
| `*.tres.remap` | 仅当导出开启「文本资源转二进制」时出现，指向 `.godot/exported/<hash>.res` | Godot 导出器 | ❌ 不用（见坑 6-2） |

> 官方对 `.tres` 的定位：
> 「资产导入器将为 `.skel` 或 `.spine-json` skeleton文件创建 `SpineSkeletonFileResource`，为 `.atlas` 文件创建 `SpineAtlasAssetResource`...
> 在导入源文件后，现在可以创建一个 `SpineSkeletonDataResource`，它结合了 `SpineSkeletonFileResource` 和 `SpineAtlasResource` 以供 `SpineSprite` 使用。」
> 并且警告：
> 「**不要**将 skeleton 数据资源定义为 `SpineSprite` 中的内联(inline)资源，因为这将成倍增大游戏所需要加载的数据量。」
> → <https://zh.esotericsoftware.com/spine-godot/markdown>（「导入至Godot」节）

- [ ] **`project.godot` 里确认**（本地已有此坑记录）：
      ```ini
      [editor]
      export/convert_text_resources_to_binary=false
      ```
      否则包里会变成 `.tres.remap` + `.godot/exported/*.res`，与官方 pck 结构对不上
      → 本地实测：`docs/踩坑指南.md:443-454`（坑 6-2，实测 88.4% → 96.4%）

## 9. 补记：引擎对**角色**到底要求哪几条动画（主会话独立实测，2026-10-06 追加）

> 本节由主会话在原调查完成后追加，证据来源与前面各节**独立**（反编译 `sts2.dll` 引擎源码 + 本仓库骨骼二进制 + 游戏日志）。**原调查正文未改动**；本节正好补上第 8 节未确认项里的第 1 条。

### 9.1 ★ 状态图**直接按名字引用**，不是推测

出处：`MegaCrit.Sts2.Core.Models.CharacterModel`（反编译 `sts2.dll`）

**(a) `GenerateAnimator()` 的基础状态图（`CharacterModel.cs:249-268`）**

| 代码原文 | 动画名 | 触发条件 | 我们的战斗骨骼 |
|---|---|---|---|
| `new AnimState("idle_loop", isLooping: true)` | `idle_loop` | 常态循环 | ✅ 有 |
| `new AnimState("low_health_loop", isLooping: true)` | `low_health_loop` | `IsLowHealth(creature)`（HP ≤ 25%） | ❌ **缺** |
| `new AnimState("die")` | `die` | `AddAnyState("Dead", …)` | ✅ 有 |

**(b) `AnimationStates` 默认表（`CharacterModel.cs:229-235`）**

**(c) `AnimState` 常量族**（`MegaCrit.Sts2.Core.Animation.AnimState`）：
`attack` / `cast` / `die` / `hurt` / `idle_loop` / `low_health_loop` / `revive` / `stun`

**⇒ 我们实缺 3 条**：`low_health_loop`（**正常游戏必然遇到**）、`revive`、`stun`（仅在对应事件发生时才被查找）

> ✅ **我们的角色没有覆写这套名字**：`Orca.GenerateAnimator`（`OrcaCharacterCode/Core/Orca.cs:93-116`）只做一件事 —— 按当前皮肤换掉骨架资源（`controller.SetSkeletonDataRes(...)`），然后 `return base.GenerateAnimator(controller, creature);` ⇒ 动画名集合就是引擎默认集。

### 9.2 ★「防御 / Defend」**不是**角色动画名（省工结论）

全引擎 grep `"block"` / `"Defend"` 共 14 次命中，**逐条都与"角色骨骼动画"无关**：

| 出处 | 它其实是什么 |
|---|---|
| `BlockConsoleCmd.cs:14` | 调试控制台命令名 |
| `CardKeyword.cs:14`、`CardTag.cs:27` | 卡牌机制（关键词 / 让卡牌算作"Defend 牌"） |
| `BlockVar.cs:12,17`、`DynamicVarSet.cs:24` | 卡牌变量名 `"Block"` |
| `IntentAnimData.cs:47,104` | `defend` = **敌人意图动画**（怪物侧），不是角色动画 |

**⇒ 想给奥卡加"防御动作"不需要新动画名**（引擎根本不会去骨架里找它）；挡格表现走音效 / 特效（本模组已有 `OrcaCharacter/audio/orca_block.tres` 音效槽）。

### 9.3「补一整套动作」的工作量口径（给排期用）

- 两套皮肤**各缺 3 条** = 6 条动画；但两套皮肤**共用同一套骨骼与图集结构** ⇒ 在 Spine 里是 **2 个工程各加 3 条动画**，不是 6 份独立工作。
- **优先级**：`low_health_loop` 先做 —— 每次残血必然触发，日志每次都警告；`revive` / `stun` 看玩法是否真会出现（敌人能不能眩晕奥卡、奥卡有没有复活机制）。
- **名字必须逐字一致**：`SkeletonData.findAnimation` 是**精确查找、无别名、无回退**（见原调查 §5.2）；写成 `lowHealthLoop` / `low-health-loop` 一律无效，且只会继续打 warning。
- 两套皮肤的导入参数不同（见原调查 §2「本工程具体的两个前提」）：板甲 `scale:0.8`、婚纱 `scale:0.9`，**填错会导致尺寸/边缘错误**。

### 9.4 与原调查第 8 节「未确认」清单的呼应

- **第 8 节第 1 条**（`low_health_loop` 在官方 wiki 上找不到出处）：本节用**引擎源码**补上了 —— 它本来就是**代码层字面量**（状态图里的字符串），可以预期 wiki 不会单独写它。但「本地 wiki 摘录在 `## Spine` 标题处截断」那件事仍值得补抓（原调查已如实记录）。
- **第 8 节第 7 条**（`character_select` / `rest_site` 骨骼的完整动画名表未列全）：与"补战斗动画"这个目标无关；若以后要改选人 / 商店 / 火堆动画，需要另做一次真正的二进制解析（本节的清单只覆盖**战斗**骨骼）。
