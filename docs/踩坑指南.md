# 银龙奥卡 · 踩坑指南（构建 / 发布 / 排查）

> **口径**：操作手册。每条坑统一四段 —— **现象 → 根因 → 正确做法 → 校验命令**。
> 目的：以后遇到同类问题直接查表，不必重推；新会话开场先读本文。
>
> **正本位置**：仓库 `docs/踩坑指南.md`（随工程走）。
> 工作区同名文件是镜像副本，**以仓库版为准**；两处内容不一致时改仓库版再同步。

## 1. 工程骨架

### 坑 1-1　参照物选错：照了一个"不含 Spine"的 mod

- **现象**：工程结构怎么摆都别扭；导出的 pck 缺资源；反复怀疑代码。
- **根因**：参照的是 `StS2-NotEnoughDifficulty`（其 pck 仅 22 KB 本地化，**不含 Spine/FMOD 资源**），
  而本 mod 的资源树里有 Spine 骨骼动画。它跑得通，不代表这套流水线对本 mod 成立。
- **正确做法**：**以官方模板为准** —— `Alchyr/ModTemplate-StS2`（BaseLib 作者维护）：
  ```powershell
  dotnet new install Alchyr.Sts2.Templates
  dotnet new alchyrsts2charmod --ModAuthor <作者> -o <临时目录>   # 生成一份对照工程
  ```
  拿它和本工程逐项对照：`csproj` / `Directory.Build.props` / `Sts2PathDiscovery.props` /
  `export_presets.cfg` / `project.godot` / `.gitignore` / `.gitattributes` / 目录分法。
- **校验**：`dotnet new list | Select-String alchyr` 能列出三个模板；对照工程能生成。

### 坑 1-2　源码平铺

- **现象**：69 个 `.cs` 全在一个目录，文件名靠前缀区分（`Cards-Pack2-B.cs`、`OrcaPowers2.cs`）。
  人看不懂，AI 也定位不准。
- **根因**：从产物反推目录，而不是按工程约定组织。
- **正确做法**：官方约定是 **`<模组名>Code/<功能>/`**：
  ```
  OrcaCharacterCode/{Core,Cards,Powers,Patches,Epochs,UI,Relics,Audio}/
  ```
  资源同理：**`<模组名>/`** 作为 Godot 资源根（`res://` 的根就是仓库根）。
- **校验**：`Get-ChildItem $Repo\OrcaCharacterCode -Directory` 每个目录职责单一、名字即用途。

### 坑 1-3　路径写死

- **现象**：换机器 / 换安装位置就编不过；仓库里出现 `D:\Steam\...`。
- **根因**：把"本机事实"写进了"工程配置"。
- **正确做法**：工程侧只引用符号；本机路径交给 `Sts2PathDiscovery.props` **自动发现**：
  1. 注册表 `HKLM\...\Uninstall\Steam App 2868840` → `InstallLocation`
  2. `HKCU\Software\Valve\Steam@SteamPath` → `steamapps`
  3. 都可被 `/p:Sts2Path=...` 或本机配置覆盖
- **校验**：
  ```powershell
  dotnet msbuild $Repo\OrcaCharacter.csproj -getProperty:Sts2Path,Sts2DataDir,ModsPath -nologo
  ```
  三个属性都应有值，且仓库里搜不到本机绝对路径。

### 坑 1-4　本机配置机制做了两套

- **现象**：同时存在 `Directory.Build.props`（入库）和 `local.props`（gitignore），都能放 `GodotPath`。
  两处可写同一常量 ⇒ 迟早不一致。
- **根因**：没先看官方约定就自己加机制。
- **正确做法**：官方模板的 `.gitignore` **包含 `Directory.Build.props`** —— 即它是本机文件。
  收敛成一套：`Directory.Build.props` 存 `GodotPath` 等本机事实，`Sts2PathDiscovery.props` 入库做自动发现。
- **校验**：`git check-ignore -v $Repo\Directory.Build.props` 应显示被忽略；全仓库搜 `GodotPath` 只出现一处。

### 坑 1-5　`.gitignore` 过肥 + `.godot/` 的处置

- **现象**：`.gitignore` 比官方模板大 8 倍；又不确定 `.godot/` 该不该忽略。
- **根因**：把"通用最佳实践"直接套上来，没按本工程实际情况判断。
- **正确做法**：
  - `.gitignore` 以官方模板为基线，只按需增补。
  - **`.godot/` 官方是忽略的**（导入缓存可重建）—— 但**本工程必须保留一个偏离**，见下。
- **校验**：`git status --short --ignored` 里 `.godot/mono/` 被忽略、`.godot/imported/` **在版本控制中**。

### ★ 必须保留的偏离：本工程要入库 `.godot/imported/`

- **现象**：官方做法忽略 `.godot/`，照做后 pck 里的卡牌立绘没有任何来源。
- **根因**：本工程资源树里，**卡牌立绘只有 `.png.import`，没有 `.png` 源图**：
  ```
  images/powers/*.png                 ← 源图在 ✓
  images/packed/card_portraits/orca/*.png.import   ← 只有 .import，源图不在本仓库 ✗
  ```
  源图属**另外两个美术模组**（`奥卡卡图`、`奥卡皮肤-Orca`），本工程按边界不持有、不修改。
  于是 `.godot/imported/` 里的 `.ctex` 是这些资源**唯一**的可用形态。
- **正确做法**：仓库保留 `.godot/imported/` 与 `.godot/exported/`，只忽略 `.godot/mono/`（编译产物）。
  `.gitattributes` 里为 `.png/.ctex/.res/.mp3str/.spatlas/.spskel` 显式标注 `binary`，防止 EOL 归一损坏。
- **校验**：`git ls-tree -r --name-only HEAD | Select-String '^\.godot/imported'` 有条目；
  `git ls-tree -r --name-only HEAD | Select-String '\.godot/mono'` 为空。

### 坑 1-6　三件套的资源边界

- **现象**：改着改着就动到了别人的美术资源。
- **根因**：本 mod 的 pck 里**确实包含**来自美术模组的资源（被"收"进来了），容易被误当自有资产。
- **正确做法**：记住边界 ——
  | 归属 | 内容 |
  |---|---|
  | **本工程** | 代码 / 本地化 / 场景与材质定义 / 着色器 / 皮肤定义 json / 音效 |
  | `奥卡卡图` | 卡牌立绘等美术位图 |
  | `奥卡皮肤-Orca` | `animations/`（图集、骨骼）、皮肤管理器 |
  **不读、不改、不复制**他人的美术。要新增美术时先确认归谁。
- **校验**：任何改动前先问一句"这个文件是谁的"；`git status` 里不应出现 `animations/**` 的位图改动。

## 2. 构建与发布流水线

### ★★ 坑 2-1　dll 与 pck 必须同源重建

- **现象**：改动明明生效了游戏却没变；或"改了 X 所以 Y 变了"这类结论全部对不上。
- **根因**：`dll`（MSBuild 编）与 `pck`（Godot 导）是**同一棵源码树编出的两个独立产物**。
  混用不同代的 dll / pck **不会当场报错**，但会让**任何行为差异都无法归因**。
  本工程实际踩过：同一份 `cards.json` 同时存在三个版本（官方 pck 6189 / 中途重打包 6288 / 仓库 6293）。
- **正确做法**（官方文档原文）：
  > *"You must publish your mod every time you make any non-code changes. Just pressing `Build` is not enough."*
  > *"If you modify only `.cs` code files, you can `Build` instead."*
  ```powershell
  dotnet build      # 只改 .cs 时用：只编 dll 并复制到 mods
  dotnet publish    # 任何非代码改动（文本/图片/场景）必须用：同时重建 dll 与 pck
  ```
- **校验**：部署后确认两个产物的时间戳同批；
  ```powershell
  Get-ChildItem $ModDir | Select-Object Name,Length,LastWriteTime
  ```

### ★★ 坑 2-2　引擎必须是 MegaDot，不是标准 Godot

- **现象**：`dotnet publish` "成功"，但 pck 从 54 MB 缩到 **2.5 MB（丢 95.4%）**；
  日志里是 warning 而不是 error。
- **根因**：游戏是 **MegaDot**（Mega Crit 定制 Godot，带 **Spine** 与 **FMOD** 模块）。
  标准 Godot 没有这些模块，**读不了 `.spatlas`/`.spskel`/`SpineSkeletonDataResource`，于是静默丢弃**。
  游戏根目录的两个 DLL 就是证据：
  ```
  libspine_godot.windows.template_release.x86_64.dll
  libGodotFmod.windows.template_release.x86_64.dll
  ```
- **正确做法**：
  1. 从 https://megadot.megacrit.com/ 取**与本机游戏匹配的** MegaDot（`/api/` 列版本，`/api/<版本>/` 列文件），
     校验同目录下的 `.sha256`。
  2. Windows 编辑器包名形如 `megadot-<版本>-windows-x86_64-llvm-editor-csharp.zip`，
     导出模板形如 `megadot-<版本>-mono-export-templates.tpz`。
  3. `GodotPath` 指向该 exe。
- **校验**：
  ```powershell
  & $GodotPath --headless --version          # 应回显 MegaDot 版本
  # 导出后比对条目数，不能靠"进程没报错"
  ```

### ★★ 坑 2-3　`ContinueOnError` 静默吞掉失败的导出

- **现象**：一次失败的导出把**可用的 54 MB pck 覆盖成 2.5 MB 残包**，构建却"成功"。
- **根因**：`<Exec ... ContinueOnError="WarnAndContinue" />` —— Godot 以 `-1` 退出，MSBuild 只记了条 warning。
  （这条是从官方模板/参照工程抄来的，**它本身也有这个隐患**。）
- **正确做法**：导出到**暂存目录**，校验产物存在，**才**复制到 mods；任何一步失败必须让构建失败：
  ```xml
  <MakeDir Directories="$(PckStagingDir)" />
  <Delete Files="$(PckStagingPath)" ContinueOnError="WarnAndContinue" />
  <Exec Command="&quot;$(GodotPath)&quot; --headless --export-pack &quot;BasicExport&quot; &quot;$(PckStagingPath)&quot;" />
  <Error Text=" Godot 导出未产出 .pck" Condition="!Exists('$(PckStagingPath)')" />
  <Copy SourceFiles="$(PckStagingPath)" DestinationFolder="$(CustomModsPath)" />
  ```
- **校验**：故意把 `GodotPath` 改成不存在的路径 → `dotnet publish` **必须失败**，且 mods 目录里的旧 pck 未被破坏。

### 坑 2-4　`AfterTargets="PostBuildEvent"` 挂不上

- **现象**：自动部署 Target 写了但从不触发，`dotnet build` 后 mods 目录没变化。
- **根因**：`AfterTargets="PostBuildEvent"` 依赖 `PostBuildEvent` 这个 target 真的运行；
  本工程没定义构建后事件，于是挂不上。
- **正确做法**：用 `AfterTargets="Build"`。
- **校验**：`dotnet build` 输出里出现该 Target 的 `Message`；目标目录出现新文件。

### 坑 2-5　增量构建的"0 错误"是假的

- **现象**：改了源码，构建报 0 错误，但产物没变（日志里是 `正在跳过目标 CoreCompile`）。
- **根因**：增量构建判定无需重编。
- **正确做法**：验证编译性时用能强制重编的方式（`-t:Rebuild`，或删 `obj/`），别拿增量结果当结论。
- **校验**：构建日志里**不能**出现 `正在跳过目标 CoreCompile`。

### 坑 2-6　编译产物混进版本库

- **现象**：仓库体积暴涨、diff 噪声大。
- **根因**：Godot.NET.Sdk 的输出落在 `.godot/mono/temp/bin/`，人容易漏掉。
- **正确做法**：忽略 `.godot/mono/`（但**不要**忽略整个 `.godot/`，见坑 1-5 的偏离）。
- **校验**：`git ls-tree -r --name-only HEAD | Select-String '\.godot/mono'` 应为空。

## 3. 排查方法论（比技术更常踩）

### ★★ 坑 3-1　拿"工作区的文件"当"部署包的内容"

- **现象**：基于某文件推断部署包行为，结论全错。
- **根因**：部署的 `.pck` 出自**另一个暂存目录**，与工作区文件并非同一份。
  实测：工作区 `pck-root` 只有 7 个文件，而部署的 pck 有 348 个条目。
- **正确做法**：**任何关于"游戏实际读到了什么"的判断，必须从部署产物里取证据**，不能从工作区推断。
- **校验**：解包部署产物再比对，而不是读工作区同名文件。

### ★★ 坑 3-2　同一份数据有多个版本

- **现象**：`cards.json` 三个版本（6189 / 6288 / 6293）在三个地方流窜，谁都不等于谁。
- **根因**：**没有一条确定性的"源码 → 构件 → mods"流水线**，中途出现了手工拷贝。
- **正确做法**：先建流水线，再谈修 bug。流水线建立前，任何"改了 X 所以 Y 变了"都不可采信。
- **校验**：源码里的文件与部署产物里的对应文件**逐字节一致**（除非本次确实改了它）。

### ★★ 坑 3-3　观测工具在骗人

- **现象**：一个"本地化文件全部非法 JSON"的结论，差点变成一次大改。
- **根因**：`Get-Content -Raw` 不指定编码时按系统默认（GBK）读 **UTF-8** 文件 ⇒ 中文变乱码、JSON 语法被读崩。
  同类：`Get-Content` 显示 UTF-8 中文乱码，据此以为文件写坏了（实际完好）。
- **正确做法**：读文本一律显式指定编码；或用 `read` 工具（按 UTF-8 读）。
  **凡"文件坏了"的结论，先用第二种方式复核一遍。**
- **校验**：
  ```powershell
  Get-Content <文件> -Raw -Encoding UTF8 | ConvertFrom-Json | Out-Null   # 不抛异常即合法
  ```

### ★★ 坑 3-4　一次改两个变量

- **现象**：多个假设都"验证"了，但没有一个站得住。
- **根因**：同时换了 `dll` 和 `pck`，之后每一轮都在测不同代的组合。
- **正确做法**：**一次只改一个变量**；换之前先明确"这次唯一的变量是什么"。
  若确实必须同时改，先留一份可比对的基准。
- **校验**：能一句话说清"这次相比上次只变了哪一个东西"。

### ★★ 坑 3-5　没核实就下结论

- **现象**：两小时内推翻自己两个"已定位的元凶"（`strike.png.import`、手工伪造的 `.ctex`）。
- **根因**：从"看起来可疑"直接跳到"就是它"，跳过了核验。
- **正确做法**：**先写清"如果它是元凶，应该能观测到什么"，再去观测。** 观测不到就撤回结论，并说明撤回了什么。
- **校验**：每个结论都能指到一条具体命令的输出。

### 坑 3-6　在错误层面深挖

- **现象**：花大量时间比对反编译结果、怀疑代码逻辑，而问题在工程形态。
- **根因**：把"工程不可复现"误判成"代码有 bug"。
- **正确做法**：**顺序是 —— 同源（源码=构件） → 可复现（一条命令重建） → 才谈代码逻辑。**
- **校验**：能一条命令从零重建出与游戏目录一致的构件。

### 坑 3-7　长命令静默无输出，就当它成功

- **现象**：文件下载"跑了"几分钟，文件却是 **0 字节**；`git push` 没报错，远端却还是旧提交。
- **根因**：为了日志干净加了静默参数（`curl -s`）、或把输出管道给了 `Select-String` 过滤，
  **失败信息被自己屏蔽掉了**。命令的"没输出"被误读成"没问题"。
- **正确做法**：
  - 长任务的进度**主动查**（文件大小、时间戳、进程 CPU），不要靠命令回显。
  - 关键步骤（推送、下载、导出）**保留完整输出与退出码**；过滤输出时同时看 `$LASTEXITCODE`。
  - 大文件下载用 `Invoke-WebRequest`，并在 PS 5.1 下加 `$ProgressPreference='SilentlyContinue'`
    （关掉进度渲染，速度差异很大）；`curl` 在某些服务端会 0 字节卡死。
- **校验**：
  ```powershell
  Get-ChildItem $out | Select-Object Name,Length,LastWriteTime     # 大小必须真在涨
  git rev-parse --short HEAD; git rev-parse --short origin/main    # 推送后两者必须相同
  ```

### ★★ 坑 3-8　"文件存在且非空"当成"已完成"

- **现象**：脚本里写 `if (Test-Path $f -and (Get-Item $f).Length -gt 0) { 跳过 }`，
  结果一个被中断留下的 **13.6 MB 半包**（目标是 551.4 MB）通过了检查，**整个下载被静默跳过**，
  而脚本只打印一句"已存在"，看起来一切正常。
- **根因**：**完成判据与"完成"不等价**。文件非空只说明"写过一点"，不说明"写完了"。
  这与坑 2-3（`ContinueOnError` 吞掉失败导出）是同一类错误：**用弱判据替代强判据，把失败读成成功。**
- **正确做法**：
  - 下载类任务：有官方校验值就用校验值当判据（如 `.sha256`），**一致才跳过**；不一致则续传或重下。
  - 产物类任务：判据是"产物可被使用"（能被解析、条目数合理、大小在预期量级），而不是"文件存在"。
  - 检测到半包要**先删再下**，别在毒产物上续做。
- **校验**：
  ```powershell
  $want = ((Invoke-WebRequest "$url.sha256" -UseBasicParsing).Content -split '\s+')[0].Trim().ToLower()
  $got  = (Get-FileHash $out -Algorithm SHA256).Hash.ToLower()
  if ($got -ne $want) { throw "产物不完整：$out" }     # 该抛就抛，别静默跳过
  ```

### 坑 3-9　PS 5.1 的 `Invoke-WebRequest -OutFile` 看起来像卡死

- **现象**：下载大文件（数百 MB）时，目标文件长时间停在 **0 字节**、内存占用飙升，
  看起来像网络卡死；换 `curl -s` 也不见字节增长。
- **根因**：Windows PowerShell 5.1 的 `Invoke-WebRequest -OutFile` 会**先缓冲再落盘**，
  大文件期间磁盘上看不到进度；`-s` 又把 curl 自身的错误信息屏蔽掉，
  于是"没输出"被读成"没进展"。（实测该服务器完全正常：Range 请求 338 KB/s、HttpClient 流式 171 KB/s。）
- **正确做法**：
  - 大文件优先用 `curl`（**不要 `-s`**），配 `-C -` 断点续传、`--retry`、`-A` 指定 UA；
  - 需要脚本化时用 `HttpClient` + `FileStream` 流式写盘；
  - PS 5.1 下若要沿用 `Invoke-WebRequest`，加 `$ProgressPreference='SilentlyContinue'` 并做好等待预期。
  - **进度一律主动查文件大小**，不依赖命令回显（与坑 3-7 同源）。
- **校验**：
  ```powershell
  # 隔一会儿看两次，大小必须在增长
  1..2 | ForEach-Object { (Get-Item $out).Length; Start-Sleep 15 }
  ```

## 5. 本工程相对官方模板的偏离（必须保留，理由在此）

| 偏离 | 理由 |
|---|---|
| 入库 `.godot/imported/` 与 `.godot/exported/` | **它们是源数据的可逆封装**，`tools/restore-sources.py` 可无损还原成源文件（见坑 6-1）；入库可保住这份"唯一副本" |

## 6. 资源重建：让 `.pck` 从零再现（实战记录）

**起点**：独立导出 `2,518,204 B / 188 条目`（官方 `54,635,766 B / 340 条目`，达成 4.6%）。
**终点**：`52,648,296 B / 261 条目`（达成 **96.4%**），且全部差异已逐条归因。

### ★★ 坑 6-1　导入产物就是源文件本身（四种格式全部可无损还原）

- **现象**：源图缺失 ⇒ 资源进不了包。看起来只能"重画"或"放弃"。
- **根因**：**误判了 `.godot/imported/` 里那些产物的性质** —— 它们不是编译中间品，而是
  **源数据的可逆封装**；Godot 的导入器只是给源数据套了一层头。
- **正确做法**：按格式剥离（工具 `tools/restore-sources.py`，带形态断言，不符即报错不产垃圾）：

  | 产物 | 结构 | 还原方式 |
  |---|---|---|
  | `.ctex` | `GST2` 头 56 B + **lossless WebP（VP8L）** | 剥离 56 B → 转 PNG（**无损**） |
  | `.spatlas` | JSON 外壳 `{"atlas_data": "<图集文本>"}` | 取 `atlas_data` 字段 |
  | `.spskel` | 8 B 头 + Spine 数据（偏移 9 起是版本号如 `4.2.43`） | 剥离 8 B |
  | `.mp3str` | `RSRC` 头 + 内嵌 MP3 | 剥离头（载荷起点需用**连续帧同步**判据确认，勿凭宽松匹配） |

- **校验**：还原后 Godot 能正常导入（Spine 导入器对格式错误会明确报错）。
  ```powershell
  python tools/restore-sources.py --repo . --dry-run   # 先看会做什么
  python tools/restore-sources.py --repo .             # 已有源文件自动跳过
  ```

### ★★ 坑 6-2　`editor/export/convert_text_resources_to_binary` 默认值决定包结构

- **现象**：`.tres`/`.tscn` 明明存在，包里却是 `.tres.remap` + `.godot/exported/*.res`；
  与官方 pck（**原样 `.tres`/`.tscn`**）结构对不上，体积也少 4.3 MB。
- **根因**：Godot 默认开启「文本资源转二进制」，导出时把文本资源转二进制并在原路径放 `.remap`。
- **正确做法**：在 `project.godot` 关掉：
  ```ini
  [editor]

  export/convert_text_resources_to_binary=false
  ```
- **校验**：**实测 88.4% → 96.4%**（`48,307,932 B` → `52,648,296 B`）；包里应不再有 `.tres.remap`。

### ★★ 坑 6-3　Spine 支持来自游戏目录的 GDExtension，不是 MegaDot 自带

- **现象**：换了 MegaDot（官方定制 Godot）后，Spine 资源**仍然**导不出来。
- **根因**：导出日志给出决定性一行 ——
  ```
  ERROR: Cannot get class 'SpineSkeletonDataResource'.
  ```
  Spine 能力由**游戏根目录的 `libspine_godot.windows.template_release.x86_64.dll`**（GDExtension）提供，
  **MegaDot 本身没有**。独立工程没加载该扩展 ⇒ Spine 资源全部剔除。
- **正确做法**：接受它，归为「依赖游戏自有资源」。**运行时游戏本体 pck 与本 mod pck 一起挂载，
  该类资源自然解析得到** —— 对 mod 而言这不是缺陷。
- **校验**：导出日志里 `SpineSkeletonDataResource` 相关报错只出现在 `.godot/` 中间产物上，不影响最终可用性。

### ★★ 坑 6-4　PS 5.1 写配置文件会加 BOM，Godot 直接读崩

- **现象**：`godot --headless --export-pack` 报 `ERROR: Invalid export preset name: BasicExport.`，
  并称「预设列表为空」—— 而 `export_presets.cfg` 打开看**完全正常**。
- **根因**：用 Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` 改过该文件，**它会写入 UTF-8 BOM**；
  Godot 的 config 解析器遇到 BOM 就认不出第一行 `[preset.0]`。文件"看起来正常"，实际开头多了 3 字节。
- **正确做法**：改配置一律用不带 BOM 的方式写：
  ```powershell
  $t = Get-Content $cfg -Raw -Encoding UTF8
  [IO.File]::WriteAllText($cfg, $t, (New-Object Text.UTF8Encoding($false)))   # $false = 不写 BOM
  ```
  **改完必须验：**
  ```powershell
  $b=[IO.File]::ReadAllBytes($cfg)
  if($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF){ throw '有 BOM' }
  ```
- **校验**：导出日志出现 `[ DONE ] savepack` 且 `exit=0`。

### ★★ 坑 6-5　"导出失败"要先查是不是**自己的比对口径**错了

- **现象**：曾判定「独立导出无法重建本 pck」，并准备改走「官方 pck 作基底 + 增量」的绕路。
- **根因**：**三条独立误判叠加** ——
  1. 把"源图缺失"当成了"美术不在手里"（其实美术以 `.ctex` 形式完整存在）；
  2. 没查 `include_filter` 无效的真实原因（是 BOM，不是 filter）；
  3. 用产物**哈希名**做对照 ⇒ 重新导入必然换名，把"命名差异"读成了"缺失"。
- **正确做法**：对照按**逻辑资源**（剥掉产物哈希后缀）比；判"缺失"前**把日志里的
  `savepack | 保存文件：…` 行也看一遍** —— 我只看 ERROR 行，漏掉了"其实已经导出、只是格式不同"这一大类。
- **校验**：
  ```powershell
  python tools/compare-pck.py --mine <本工程.pck> --official <官方.pck> --out docs/对照报告.md
  ```
  → 报告里 `? 待查明` 必须为 0。

### 坑 6-6　「逐条对照 340 条目」这个验收口径本身要修正

- **现象**：达到 96.4% 后仍剩 114 条差异，字面上"没通过"。
- **根因**：官方那 340 条目/54.6 MB 是在**游戏工程资源可用的环境**里构建的
  （作者的工程很可能嵌在游戏工程内），里面混着**游戏本体与另外两个模组的资源**，以及产物哈希名。
  **这些差异在 mod 的独立工程里不可能、也不应该被消除。**
- **正确做法**：验收口径改为 **「每条差异都有已证实的原因，且无功能性缺口」**，并在报告里区分两栏：
  **「环境导致的差异」**（游戏/其它模组/产物命名/进包策略）与 **「有意改动」**（本工程真正改了什么）。
- **校验**：报告分类表中 `D 源文件尚未还原` 与 `? 待查明` 均为 0。
