### 2.12 焚烧的结算口径（新权威新增 `说明1:46`）—— 本轮核对结论：**范围一致、计数等价**

**新权威原文**（两条合起来看）：

- `说明1:46`（**本轮新增的唯一一行**）：
  > 备注：假如有一残血+一满血，两个带标记，应该是计算场上所有的【焚烧层数】总和与总【焚烧】标记目标，然后对带【焚烧目标】造成伤害（总【焚烧】标记目标）次，防止出现类似残血先结算死亡，导致满血结算的时候出现少算一次【焚烧】的情况

**代码实际**（`OrcaBurnAndEcho.cs:110-187`，`Burst` 是唯一结算实现）：

```csharp
var snapshot = burning                                     // L121-124：先把每个带焚烧者的层数**冻结**成快照
    .Select(c => (Target: c, Stacks: (int)(c.GetPower<OrcaBurnPower>()?.Amount ?? 0)))
    .Where(t => t.Stacks > 0).ToList();

foreach (var (src, stacks) in snapshot)                    // L156：按快照**逐源**结算（源中途死了也不跳过）
{
    alive = snapshot.Select(t => t.Target).Where(c => !c.IsDead).ToList();   // L168：只打【带焚烧】的目标
    await CreatureCmd.Damage(choiceContext, alive, (decimal)stacks, ...);    // L178：每段伤害 = 该源自己的层数
}
```

**逐条核对**

| 新权威要求 | 代码位置与行为 | 判定 |
| --- | --- | --- |
| 对**带【焚烧】目标**造成伤害（不是"所有敌人"） | `:168` `alive = snapshot…Where(!IsDead)` —— 只波及带焚烧的标记目标 | ✅ 一致（顺带把上一轮"无法判定 #9『敌人全体』指谁"判掉：**新权威自己明确成了"带焚烧标记的目标"**） |

| 「防止残血先结算死亡 ⇒ 满血那边少算一次」 | 层数已被快照冻结、循环不跳过已死源 ⇒ 存活目标不会少挨 | ✅ 该风险在本实现里**不成立** |

**如实记录的两处非数值差异**：
1. `:175` 的 `/*TOGGLE-OFF-A2*/ break;`：当"所有标记目标都已死亡"时会提前跳出 —— 此时已无目标可打，**数值无影响**（这也是它被列入"故意保持关闭"名单的原因）。
2. `:178` 允许用"快照里已死的 src"作为伤害来源执行一次 —— 只影响日志归属，不影响伤害数值。

> **读法提示（若与本审计判法不同，需用户一句话确认）**：新备注「计算场上所有层数总和…对带【焚烧】目标造成伤害（总标记目标）次」有两种读法：
> ① 每段伤害 = 各源自身层数 ⇒ 某个存活目标累计挨到 **A**、共 **B** 段（**代码就是这种**；用备注自己的例子「一残血 + 一满血，2 层 + 5 层」= 每个存活目标挨 7 点）；
> ② 每段伤害 = **A** 点、共 **B** 段 ⇒ 每个目标挨 **A×B**。
> 本审计按 **①** 判「一致」。若你的本意是 ②，请说一声 —— 那代码就要改成"先算 A 与 B，再对每个标记目标打 B 次 A 点"。
